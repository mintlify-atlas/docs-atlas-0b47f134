title: "Design patterns used in Relay"
description: "How Relay applies six design patterns — Strategy, Observer, Factory, Builder, Singleton, Decorator — to real problems in the chat backend and frontend."
---

Relay uses six classic design patterns, each applied to a real problem in the codebase rather than adopted for its own sake. The patterns span both the NestJS backend and the Next.js client: some govern how data is stored, some govern how events propagate across the WebSocket layer, and some keep authentication concerns from leaking into business logic. The Prototype pattern was considered and deliberately skipped — there was no honest use case for it.

## Pattern summary

| Pattern | Problem solved | File location |
|---|---|---|
| **Strategy** | Swap chat storage (Prisma vs in-memory) without touching the rest of the app | `relay-backend/src/chat/storage/` |
| **Observer** | Decouple database writes from Socket.io broadcasting via RxJS Subjects | `relay-backend/src/chat/chat.service.ts`, `chat.gateway.ts` |
| **Factory** | Eliminate a sprawling `switch` in the gateway when creating message variants | `relay-backend/src/chat/` _(designed, implementation pending)_ |
| **Builder** | Replace a 6-argument message constructor with a readable fluent API | `relay-app/lib/` _(designed, implementation pending)_ |
| **Singleton** | One database connection pool; one in-browser key cache | `relay-backend/src/common/prisma.service.ts` |
| **Decorator** | Keep auth/extraction logic out of route handlers | `relay-backend/src/common/decorators/current-user.decorator.ts` |

<Note>
  Prototype was intentionally skipped. Relay has no honest use case for cloning object graphs, and using six patterns well is more valuable than forcing a seventh.
</Note>
